Do Visual Navigators Still Need a Map?

The complete benchmark implementation is open source: Code on GitHub.

Background Problem Setup Implementation Experiments Discussion References Acknowledgements

Background

A robot that has visited a place before can use a map to guide its next journey. For large-scale navigation, however, building and maintaining that map is part of the problem: how much information must we collect before the robot can find its way reliably? Our earlier work explored lightweight visual maps as an answer. First, LiteVLoc [1] combined place recognition, feature matching, and pose-graph optimization to support autonomous, global, continuous localization on sparse topological maps. Then, OpenNavMap [2] extended this direction toward crowdsourced navigation systems. Motivated by mapping with multiple devices, it addressed landmark-free multi-session mapping so that separate traversals could contribute to a shared map. Meanwhile, frontier vision-language models such as OpenAI's GPT-6 Astra [3] make us curious about what a model can infer from the camera view and a goal image alone. Can it understand the space and steer a robot through it? Intuitively, a map should help. Yet how much a prior visual map helps, which observations are worth keeping, and whether map priors can impair the model's own navigation remain unclear. We therefore compare dense, sparse, and absent visual maps while varying access to localization in a shared image-goal navigation task.

Problem Setup

Task and evaluation scope

We use image-goal navigation to test whether a robot can connect visual recognition with movement. A goal image specifies where to go and which direction to face, allowing us to compare how different navigation methods use visual observations and prior maps. The robot must reach the place where the goal image was captured and face the same direction. We manually collect five independent routes per scene and build one prior topometric map per route, sampled at two densities. Evaluation now covers five routes in each of ENV0, ENV1 and ENV3, run once per method and route. ENV1 and ENV3 use the uniformly re-evaluated results described below.

What a topometric map contains

A topometric map stores keyframe images with their 2D poses and graph connections along recorded routes. These connections provide a prior about which transitions belong to a traversable route; they do not by themselves provide a local motion plan or a facility-control skill.

Baselines

We compare seven methods on the same Go2 robot, routes, and success criterion. Go2 carries a forward-facing RGB-D camera.

  • SRU [4] uses depth, odometry, and a target coordinate. It outputs forward and lateral velocities and a yaw rate (vx, vy, wz). It never sees the goal image.
  • VLM (GPT-6 Astra) receives only RGB images, including the goal image, with no depth, odometry, or coordinates. It outputs the same velocity commands (vx, vy, wz), plus decisions about subgoal arrival and task completion.
Table 2. Navigation methods and information available to each planner.
ID Map Localization Planner How subgoal arrival is determined
B0 Dense Continuous SRU (point goal) By ground-truth pose
M1 Sparse Continuous SRU (point goal) By ground-truth pose
M2 Dense Continuous VLM (image goal) By ground-truth pose
M3 Sparse Continuous VLM (image goal) By ground-truth pose
M4 Dense Initial only VLM (image goal) VLM decides when it has reached the current subgoal image
M5 Sparse Initial only VLM (image goal) VLM decides when it has reached the current subgoal image
M6 None None VLM (image goal) No subgoals; only the final goal image

B0/M1 isolate map density for SRU; M2/M3 replace SRU with a VLM. M4/M5 remove continuous localization, and M6 removes the map entirely. Continuous localization uses ground-truth pose to determine subgoal completion and episode termination. Initial-only localization supplies a starting pose fix, then relies on visual recognition. The VLM itself never receives pose coordinates.

Physics and locomotion

Unlike HM3D-based image-goal benchmarks [5], including Instance-ImageNav [6], we simulate Go2 with furniture, collisions, and continuous velocity commands. MoE-CTS [7], the quadruped locomotion controller, executes those commands.

Implementation

We run the experiments in NVIDIA Isaac Sim, simulating a Unitree Go2 with physics, collisions, and camera observations.

  1. Route. B0–M5 use Dijkstra's algorithm to select subgoals; M6 sees only the final goal image.
  2. Recognize progress. Continuous localization checks subgoals by pose; M4/M5 recognize arrival from images.
  3. Act and repeat. SRU [4] uses depth, odometry, and coordinates. The VLM sees the current RGB frame, up to four history thumbnails, and goal and subgoal images. Both output vx, vy, wz.

Timing and prompt

VLM commands last 1.0 s; SRU commands last 0.2 s. Simulation pauses during decisions, so compute latency does not consume the episode budget (90 s in ENV0/ENV1; 120 s in ENV3). Mapped ENV3 elevator runs use a shared depth/odometry-based transfer controller; the VLM pauses during this phase. The original VLM system prompt follows.

Full system prompt
You are the pilot of a four-legged robot (Unitree Go2) indoors. You see only through one forward-facing RGB camera (640x480, about 95 degrees horizontal field of view, mounted about 0.7 m above the floor). You control the robot by choosing a velocity command at every decision. TASK You are given a GOAL IMAGE: a photo taken by this same camera at the target place. Drive to the place where the goal image was taken and face the same direction. The episode succeeds only if, when you declare done, the robot is within 0.5 m of that place and within 45 degrees of that heading. Declaring done anywhere else is a failure, and so is running out of time. Time is limited, so move efficiently, but do not rush the final alignment. SUBGOALS (only when a CURRENT SUBGOAL IMAGE is given) A subgoal image is a photo taken earlier, during a mapping run, along a route that leads toward the goal. Drive to where the subgoal image was taken. When you are within about 1 m of that spot and your view roughly matches it, set "subgoal_reached": true; you will then be given the next subgoal image, or no subgoal image when the goal is close. Subgoal images may be several meters apart and the next one may not be visible yet: head in the direction the route is going. The goal image is always the final target. When no subgoal image is given, always set "subgoal_reached": false. ACTIONS Each decision applies your command (vx, vy, wz) for exactly 1.0 second, then you decide again. The world is paused while you think. - vx: forward speed in m/s, from 0.0 to 0.8. The robot cannot move backward. - vy: sideways speed in m/s, from -0.3 to 0.3. Positive = to the robot's left. - wz: turning speed in rad/s, from -0.7 to 0.7. Positive = turn left (counter-clockwise). Measured effect of one decision: wz 0.3 turns about 14 degrees, wz 0.5 about 28 degrees, wz 0.7 about 41 degrees. vx 0.5 moves about 0.4 m, vx 0.8 about 0.7 m. A full turn in place takes about 9 decisions. Avoid collisions: if a wall or furniture fills the lower part of the view, turn or side-step instead of going forward. If the robot falls over, the episode fails. Near the goal, use small speeds to line up. WHAT YOU RECEIVE EACH DECISION - GOAL IMAGE, and CURRENT SUBGOAL IMAGE if any. - PAST FRAMES: up to 4 smaller (320x240) frames from 8, 4, 2 and 1 decisions ago, oldest first, labeled d-8 ... d-1. Use them to judge your own motion and to recognize places you have already seen. - CURRENT FRAME: what the camera sees now. - RECENT LOG: your last 15 commands (as executed) with the observation you wrote at each decision. - MEMORY: the note you wrote at the previous decision. - FEEDBACK: messages from the system, e.g. that your previous reply was invalid or that the subgoal changed. You get no map, no position and no depth. Rely on what you see. EXPLORING If the target is not in view, look around by turning in place, then go through doorways and along corridors toward areas you have not visited. Use MEMORY to avoid searching the same room twice. OUTPUT Reply with one JSON object only, with exactly these fields in this order: {"observation": string, at most 15 words: what you see now that matters; "target_visible": boolean, true if the place in the current target image (the subgoal image if given, otherwise the goal image) is visible in the current frame; "subgoal_reached": boolean, see SUBGOALS; "done": boolean, true only when you are at the goal place facing the goal direction; this ends the episode; "memory": string, at most 40 words: where you have been, where the goal probably is, your plan; it is shown back to you next decision; "vx": number, "vy": number, "wz": number} When "done" is true the robot stops; your velocities are ignored.

Discussion

1. Useful maps need executable transitions

Maps help when their keyframes and connections support an actionable route; more keyframes alone are not a general solution. Dense maps outperform sparse maps for SRU in ENV0 and ENV3, while the ordering reverses in ENV1. M5 succeeds on four of five routes in every scene, but M2/M3 are stronger in some settings. One revealing case is ENV3: M6 recognizes stairs and elevators yet remains on the first floor, whereas mapped elevator runs complete the transition with a shared transfer controller. This points to the value of route structure and execution support; success cannot be credited to the map or VLM alone.

2. Progress checks must match the navigation loop

Accurate localization does not guarantee a smooth interaction with a visual planner. On ENV3 R5, M2 keeps receiving the same subgoal image for 44 decisions despite repeatedly declaring arrival: the prompt promises a new image, while the pose gate retains the old one. Conversely, accepting visual arrival too early can skip a needed transition. These cases motivate a consistent handoff that combines recognizable landmarks, reachability and route progress, with clear feedback when a subgoal is not advanced. The current runs do not isolate which cue would resolve the failures.

3. Let the robot choose its map and memory

Choosing useful keyframes and deciding what to remember could reduce human intervention throughout navigation. Our exploratory variants select maps once per route (AM), memory at each step (AMem), or both (AMM). With the same keyframe count, AM improves ENV0 success from 4/5 to 5/5; AMem reduces mean input tokens per call by 22.5% across 15 routes, but needs more calls. Each variant succeeds on 10/15 routes versus 12/15 for historical M5. These signals motivate linking selection to execution feedback, progress checks and recovery, rather than assuming selection alone is sufficient. Online map reselection remains untested.

Scope: five routes per environment, one run per cell. ENV0 is a historical baseline; ENV1 and ENV3 use a later frozen version and different scene budgets. These observations do not establish statistical or causal effects.
